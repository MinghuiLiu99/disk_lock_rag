# 盘扣架规范 RAG 知识库

面向《建筑施工承插型盘扣式钢管脚手架安全技术标准》JGJ/T 231-2021 的结构感知检索增强问答系统。

与"把 PDF 丢给通用解析器再向量检索"的做法不同，本项目把规范中的**条文、表格、公式、图**当作四类异构单元分别处理，并利用规范内部**显式可溯源的引用关系**做闭包扩展，让答案既准确又能给出法源。

> **当前状态：两本规范均已跑通**，同一套解析器，只改命令行参数。
> JGJ/T 231-2021（行业标准，57 页）381 节点；DB11/T 2100-2023（京津冀地标，75 页）422 节点。
> 两本都是 **0 校验错误、0 重复 `node_id`**。另有一个 7 页测试件用于快速回归。

|---|---|---|---|
| 页数 | 7 | 57 | 75 |
| 节点数 | 72 | **381** | **422** |
| 解析耗时 | 0.7 s | 6.8 s | 6.0 s |

两本规范的**形态差异**本身就是个发现：JGJ 偏"**计算型**"（给公式，自己算），DB11 偏"**选用型**"（给选型表，直接查）——DB11 全文 **0 个编号公式、0 个"式中"变量段**，设计参数全部做成表格。

条文说明与正文已按条号双向关联，**153 条正文中有 67 条拿到官方说明（44%）**；区间写法（`4.1.1～4.1.4`）与列举写法（`7.4.11、7.4.12`）会自动展开成多条。

## 一、要解决的问题

通用 RAG 管线在这类文档上会系统性失效。下面是同一份 PDF 的实测对比：

| | RAGFlow v0.27.2（laws 预设） | 本项目 |
|---|---|---|
| 分块结果 | 373 块，**93 块不足 10 字**，中位数 38 字 | 72 节点，0 校验错误 |
| 表格 | **79 个纯数字碎片**（表结构完全丢失） | 4 张表全部结构化，合并表头 / 转置表均正确 |
| 公式 | 符号乱码（Symbol 字体私有区编码未处理） | 14 个码位全修复 + 变量表 + 截图 |
| 条文号 | **错位**（6.2.3 的内容被并进标着 6.2.4 的块） | 正确 |

失效的根源不是模型不好，而是**文本块边界与规范的结构边界不一致**：表格被切碎、公式被拆散、条文号被换行截断。一旦切错，后面的检索和生成都无法挽回。

## 二、效果实测

在 7 页测试件上跑过的问法（累计 23 条，通过 22 条）：

| 组别 | 结果 |
|---|---|
| 事实型 / 查表型 / 公式型 / 图形型 / 跨条对比 | ✅ 全部 top-1 命中，答案正确，引用可溯源 |
| 口语化提问（5 条） | ✅ 4/5（"斜撑"失败 → 已用同义词扩展修复） |
| 对抗探针：超范围 / 规范未规定 | ✅ **正确拒答** |
| 对抗探针：枚举型（"本章哪些条文提到 X"） | ❌ 漏答（top-k 检索的固有缺陷） |

**反幻觉是实测有效的。** 探针"扫地杆距可调底座底板不应大于多少"的真实答案 550mm 位于第 6.2.5 条，不在这 7 页内——而 550mm 是模型预训练里大概率知道的常识。系统没有编造，而是拒答。这依赖三层设计：提示词约束、材料中显式标注"引用的附录不在材料范围内"、生成后的引用回查。

性能（RTX 5060 Ti 16GB + 本地 27B 模型，无 API 成本）：
模型已加载时**首字 3~4 秒、完整回答 4~14 秒**；冷启动（模型需重新加载）首字会到 15 秒左右。
实测生成速度约 **15 tok/s**，瓶颈是显存带宽（448 GB/s，128-bit GDDR7）。

## 三、架构

```
PDF
 └─ 版面解析 ──── 字符坐标聚类 → 表格还原 / 图区定位 / 公式区识别
     └─ 结构重建 ─ 符号修复 · 断行修复 · 跨页合并 · 同号合并 · 表头扁平化
         └─ 节点构建 ─ 27 字段节点 + 父子链 + 引用边 + 质量标记
             └─ 索引 ──── 向量 | BM25 | 表格库 | 引用图
                 └─ 检索 ─ 同义词扩展 → 编号硬加权 → 混合 RRF → 引用闭包扩展
                     └─ 生成 ─ 父子回填 → 带引用约束生成 → 引用回查 → 拒答
                         └─ 前端 ─ 流式答案 + 依据卡片 + PDF 原文坐标高亮
```

### 四类异构单元的处理策略

| 单元 | 检索表示（`content`） | 原文载体（`body`） | 说明 |
|---|---|---|---|
| **条文** | 整条原文 | — | 以"条"为原子单位，不按字符数切；款/项单独成节点 |
| **表格** | 扁平表头 + 行级"列名=值" | 结构化行列 + Markdown + 表注 | 合并表头压成单层，转置表还原语义，纵向合并向下填充 |
| **公式** | 语义句 + "式中"变量表 | 线性文本 + 变量表（+ 截图） | **公式本体不进向量**——符号对 embedding 无意义 |
| **图** | 图题 + 图注 | 按坐标裁切的 PNG | 矢量图靠图元聚类定位，位图接口取不到 |

## 六、节点字段规范

每个节点 27 个字段，分六组：

| 组 | 字段 |
|---|---|
| 身份 | `node_id` `standard_id` `standard_code` `standard_name` `doc_id` `version` `type` `num` |
| 定位 | `level` `chapter` `section` `path` `pages` `bboxes` |
| 内容 | `content`（检索表示）`body`（原文载体） |
| 关系 | `parent_id` `child_ids` `refs` `referenced_by` `explains` `explained_by` |
| 语义 | `modality`（严禁/必须/应/宜/可）`keywords` `keywords_source` |
| 质量 | `status` `status_reason` |

设计原则：

1. 每个字段只服务于**检索 / 生成 / 溯源**三者之一
2. 抽不到写 `null`，确定为空集合写 `[]`，**禁止空字符串**
3. `content` 与 `body` 分离——前者可以是为检索生成的代理文本，后者是给人看的原文
4. `pages` 记**原书页码**（不是文件内页码），否则无法回溯到完整版 PDF
5. `level` 由 `type` 推导，不手填

## 七、实测发现的 16 类排印陷阱

这些是通用解析器会踩、且踩了之后**不可逆**的问题。全部在 `layout.py` / `parser.py` 里有对应处理，并写进注释。
前 12 类来自 JGJ/T 231-2021，后 4 类换到 DB11/T 2100-2023 才暴露。

| # | 陷阱 | 处理 |
|---|---|---|
| 1 | 公式符号是 Symbol 字体私有区编码（本 PDF 14 个码位） | 码位映射表 |
| 2 | 矢量图被表格检测误判为表格（区域内无文字单元格） | 用"有无文字"过滤假阳性 |
| 3 | 跨页表格，表头在上页页尾（只剩 1 行 2 列） | 页尾表头 + 页首表体合并，列数补齐 |
| 4 | 跨页表的**表标题**也在上一页 | 标题随表头一起继承 |
| 5 | 单元格内下标被空格拆开（`G1+G2` → `G 1 +G 2`） | 按字符坐标重建，不用通用抽取接口 |
| 6 | 条文以"（图"结尾断行，下一行行首的 `6.2.4）` 被当成新条文 | 断行修复 + 条号负向断言 |
| 7 | 条文被表格打断，同一段出现两次条号 | 同号合并 |
| 8 | 条文跨页续接（"式中"段落跑到下一页） | 跨页归并到上一条文 |
| 9 | 表注是多行，续行没有"注："前缀 | 从"注："抓到下一条号之前 |
| 10 | 页脚页码混进条文正文 | 页边距区域过滤（页码只进 `pages` 字段） |
| 11 | 图题、图注、子图标签被当成正文 | 归属到图节点，并纳入图区坐标 |
| 12 | 合并表头（`类别 \| 连墙件布置` + `2步3跨 \| 3步3跨`） | 横向传播 + 纵向拼接压成单层表头 |

另外还有三类容易忽略的：

- **转置型表**：表头是"搭设高度"，行首是"βH"，语义方向与常规表相反，需要单独识别
- **表标题粘连**：原文写作"按表5.3.2 支撑脚手架搭设高度调整系数"，需要从粘连文本里拆出标题
- **破折号混用**：图注用 U+FF0D 全角连字符，全文其他地方用 U+2014 长破折号，不归一化会导致精确匹配失败

### 换第二本规范时新暴露的 4 个坑

从 JGJ 换到 DB11/T 2100 时，又撞了 4 个——**而且四个全部静默通过校验**（`0 校验错误`，但结果是错的）。根因都是**目录页**：JGJ 那份 PDF 没有正文目录（直接从"1 总则"开始），所以这类问题一直没暴露。

| # | 坑 | 表现 | 修法 |
|---|---|---|---|
| 13 | 目录里的"条文说明"条目 | 从第 6 页起整本被判成条文说明（244 个 explanation、**0 个 clause**） | 判据收紧为"整页字符 < 800 且该行基本就是『条文说明』"（标题页特征） |
| 14 | 目录里的"附录A"条目 | 附录 A/B/C 各重复一次 | 新增 `TOC_LINE_RE` 排除目录行 |
| 15 | **目录引导符有三种**：中文点线 `....`、英文省略号 `…………`、间隔号 `····` | 只写点线会漏掉整页英文目录 | 正则字符集覆盖全部三种 |
| 16 | 说明正文里的**引用式开头**（"6.2.3条给出此条规定…"） | 同一条说明被切成两块 | `NOTES_CLAUSE_RE` 加 `(?!条)` |

> **这 4 个坑的共同教训**：换文档时最容易失效的不是核心逻辑，而是"针对上一份文档的排印习惯写死的判据"。而且**校验器不会报错**——必须靠"节点数/类型分布是否合理"来发现。

### 多规范混库与跨规范冲突

两本规范可以进同一个索引（`--profile mixed`），节点 id 因为带 `standard_id` 前缀不会撞。混库后系统会自动切换到**多规范模式**：

| 变化 | 单规范 | 多规范 |
|---|---|---|
| 材料块头部 | `【第5.3.3条】` | `【JGJ/T 231-2021 第5.3.3条】` |
| 引用格式要求 | `[来源：第5.3.3条]` | **`[来源：JGJ/T 231-2021 第5.3.3条]`**（标准号不能省） |
| 冲突处理 | — | 提示词新增规则："不同标准规定不一致时必须分别列出并说明出处" |
| 依据卡片 | 显示条号 | 显示**标准号 + 中文全称** |

**实测效果**（问"可调托撑伸出顶层水平杆的悬臂长度不应超过多少"）：

> 不同标准对同一问题的规定不一致：
> 1. 根据《建筑施工承插型盘扣式钢管脚手架安全技术标准》，支撑架可调托撑伸出顶层水平杆或双槽托梁中心线的悬臂长度不应超过 **650mm** ［来源：JGJ/T 231-2021 第6.2.4条］。
> 2. 根据《承插盘扣式钢管脚手架安全选用技术规程》，可调托撑伸出顶层水平杆的悬臂长度不应大于 **500mm** ［来源：DB11/T 2100-2023 第6.2.6条］。

两本的差异是真实的：JGJ/T 231 允许 650mm，DB11/T 2100 收紧到 500mm。系统**没有把两者合并成一个结论**，而是分列并各自标注出处——这正是多规范场景下最容易出错、也最需要的地方。

## 八、工程上踩过的坑

1. **本机 numpy 2.5.3 的 BLAS 在 2D@1D 矩阵向量乘上原生崩溃**（`0xc06d007f`）。改用逐元素乘 + 求和（`(matrix * q).sum(axis=1)`）。
2. **引用图必须包含父子边**。只加 `refs` 边时闭包扩展一条都带不回来——"条文 → 它自带的公式"是父子关系而非引用关系。
3. **枢纽节点不能扩展**。从"节"扩展会把整节条文全拉进上下文，只从内容型节点（条/款/表/图/公式）扩展。
4. **零分的扩展节点会把高分的直接命中挤出上下文**。问"可调托撑承载力"时，表 5.1.9 被 5 条零分扩展条文挤掉，模型只能回答"材料中未规定"。改成两段填充（直接命中优先）+ 分数比例过滤。
5. **编号类查询不能交给向量**。"5.4.2 说了什么"会被语义相近的 5.4.3 抢走，必须加显式标识符硬加权。
6. **带着类型前缀的编号要先遮住再扫裸编号**。"表5.1.9"里的 5.1.9 是表号不是条号，不遮的话条文 5.1.9 也会被加权。
7. **本地生成模型默认"永远思考"**，token 预算会被 reasoning 吃光导致空答案。LM Studio 支持 `reasoning_effort: "none"` 关闭思考（取值必须是 `"none"`，`"off"` 会返回 HTTP 400），首字从 15~26 秒降到 2~4 秒，答案反而更直接。
8. **SQLite 连接不能跨线程**。`TableStore` 的索引在 FastAPI 的同步线程池里建（`def` 端点），查询却发生在异步事件循环线程（`async def` 端点），SQLite 会抛 `SQLite objects created in a thread can only be used in that same thread`——该错误让全量下的 `/api/ask` 直接 500。用 `check_same_thread=False`（建完后只读查询，单进程单请求，是安全的）。
9. **PDF 高亮要裁横带，不能放整页**。整页在 150dpi 下有 1750px 高，而证据卡片可视高度只有约 300px，高亮往往落在可视区外、看着就是一片空白（实测踩过）。改成只裁高亮上下各 90pt 的横带（1241×462），一眼可见。
10. **闭包扩展要优先走引用边并逐种子轮转**。若混着父子边顺序取，`5.4.1` 一条就带 4 款 + 3 公式 + 1 表，会把扩展预算全吃光，真正需要的附录 C（由 `5.3.3` 引用）反而拿不回来。
11. **旧结论要跟着前提走**。上下文块数上限原本设成 6，依据是"10 块材料时首字要 26.7 秒"——但那个数据是在**思考模式开着**的情况下测的。关掉思考后重测：6 块 2.4s、10 块 3.6s、20 块 4.2s，**代价几乎不存在**。于是默认值调到 10（材料多则闭包带回的公式附表更全）。差一点就把一个错误约束固化在代码里。
12. **暴露参数不等于打通参数**。给 `build_context` 加了 `max_blocks` 参数后，传 15 仍然只返回 6 块——因为函数内部还有两道硬编码上限（`[:4]` 和 `[:2]`）。改完才生效。
13. **"没编号"的节点会让混库建索引直接崩**。DB11 有两张表没识别出表号，`table_id=None`，于是关键词生成了 `['表None', None]`——`" ".join(keywords)` 抛 `TypeError`。而校验器**没拦**（`num` 为空时会跳过一致性检查）。修法：无表号时用 `['未编号表']`，并标 `need_review / table_title_missing`。**教训：可空字段要显式处理，校验器也要覆盖"字段为空"这条路径。**
14. **原文会漏印关键词**。DB11 p37 上一张表写"**表**7.2.3-1"，下一张写成"7.2.3-2"——漏了"表"字。备用判据必须**要求 `-N` 后缀**，否则会把"7.2.4 平面结构为弧线…"这种条文号也当成表题。
