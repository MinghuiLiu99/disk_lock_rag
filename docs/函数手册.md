# rag_core 函数手册

覆盖 `rag_core/` 里全部 **130 个函数与方法**。每条写四件事：

| | |
|---|---|
| **职责** | 一句话说它干什么 |
| **输入 / 输出** | 参数和返回值的数据形态 |
| **为什么存在** | 这个函数为什么会被写出来——这是本手册的主要价值 |
| **什么时候用** | 你在什么场景下会调用它，或者会去改它 |

函数签名看代码就知道，"为什么会有这个函数"看不出来。所以第三项写得最细。

---

## 怎么用这份手册

**想搞懂一个函数**：直接在文件里搜函数名，四条都在。

**想搞懂一层**：读每层开头的「这层在干什么」。

**想改代码**：先跳到最后一节「改代码时该动哪一层」，它按"你想达到什么效果"来索引。

**想按顺序学**：不要按这份手册的顺序读。按 `schema → layout → parser → tables → index → generate` 走，这是依赖方向，也是从简单到复杂的顺序。

---

## 全景

```
PDF
 ↓  layout.py      版面上这是什么          （字符 → 行 → 表/图/公式区）
 ↓  parser.py      这属于第几条            （行 → 条文树）
 ↓  tables.py      表能不能按 key 查        （表 → 可查询结构）
 ↓  schema.py      输出长什么样、彼此什么关系（→ 27 字段 + 关系边）
nodes.jsonl                                  ← 分界线，落盘
 ↓  index.py       该看哪几条              （问题 → 候选节点）
 ↓  generate.py    怎么答、标来源、何时拒答  （候选 → 答案）
```

前四个文件是**离线**的（解析一本规范跑一次），后两个是**在线**的（每次提问都跑）。

**依赖是单向的**，没有循环：

```
schema ─┐
layout ─┼─ 这三个互不依赖
tables ─┘
   ↓
parser（用三个）  index（用 schema）  generate（用 schema + tables）
```

一个能说明问题的细节：**`pdfplumber` 只被 `layout.py` 和 `parser.py` 用到**。`index.py` 和 `generate.py` 完全不知道 PDF 存在——它们只认 `nodes.jsonl`。所以哪天换 OCR，改的是上面两个，下面两个一行不用动。

## 一、schema.py —— 数据契约层

**这层在干什么**：定义"一个节点是什么"。27 个字段、10 种类型各占第几层、6 类引用怎么表示、什么情况算"待复核"。它不解析 PDF，也不检索。

**什么时候会动它**：想加字段、加节点类型、加引用类型。**这是全项目的宪法，改之前先确认下游三处（parser / index / generate）都跟得上。**

### 1.1 常量（12 个）

| 常量 | 内容 | 为什么要它 |
|---|---|---|
| `TYPE_LEVEL` | 10 种 type → 层级号：`preamble=0`、`chapter/appendix=1`、`section=2`、`clause/table/figure/formula/explanation=3`、`item=4` | 表和条**故意同级**（都是 3）——表是挂在条下面的独立知识单元，不是条的"子条款"。附录 `appendix` 也和章同级但**必须独立成类型**，否则引用里"附录A"和"第1章"分不开，`in_scope` 判定会错 |
| `ALLOWED_TYPES` | 从 `TYPE_LEVEL` 的键推导 | 所有类型判断都以它为准，改一处即可 |
| `REF_TYPES` | 6 类引用：`clause / table / figure / formula / appendix / external_standard` | 最后一类是"引别的规范"（GB 50009 这种），它**指向本知识库之外**，所以没有 target_node_id |
| `MODALITY_LEVEL` | 用词等级：严禁/必须=1，应/不应=2，宜/不宜=3，可=4 | 施工规范里"应"和"宜"是**强制性条款和推荐性条款的区别**，检索和答案必须保留。这也是这套库能谈"规范性"的前提 |
| `_MODALITY_PRIORITY` | 严格程度排序，用于取最严格者 | 一条里同时出现"应"和"可"时取"应" |
| `KEYWORD_SOURCES` | 关键词来源：`structural / extracted / llm / mixed` | 关键词是算出来的还是人工/模型给的，必须能追溯，否则不知道能不能信 |
| `STATUSES` | `ok` / `need_review` | 二值状态。**不是"成功/失败"，是"确定/待人工确认"** |
| `STATUS_REASONS` | 13 种待复核原因 | **这是全项目最值钱的一张表**，对应实测撞出来的排印陷阱。`validate_node` 强制 `need_review` 必须填原因，就是为了让复核能按类型批量做 |
| `NODE_FIELDS` | 27 个字段名，顺序即输出顺序 | 校验和序列化都以它为准 |
| `REF_FIELDS` | 引用的 5 个字段：`target_type / target_num / target_node_id / target_display / in_scope` | `in_scope` 先留 `None`，全部节点建完后由 `link_structure()` 判定——**单个节点算不出它引的东西在不在库里** |
| `DISPLAY_PREFIX` | 类型 → 中文前缀：`clause → 第{num}条`、`table → 表{num}` … | 答案里要写"依据：表5.1.9"，不能写"依据：table:5.1.9" |
| `_REF_PATTERNS` | 6 条正则，对应 6 类引用 | 每种引用在原文里长得不一样：`第4.2.1条` / `表4.2.1` / `图5.1.4` / `附录A` / `式（5.3.3-1）` / `GB 50009`。**这 6 条正则是"规范交叉引用能被检索到"的入口**，也是全项目最关键的一段正则 |

### 1.2 工具函数（3 个）

#### `node_id_of(standard_id, node_type, num, fallback=None) -> str` — L96

**职责**：拼出三段式主键 `标准代号:类型:编号`，如 `JGJ231:table:5.4.1`。

**为什么存在**：**类型段不能省**。规范里"条 4.3.1"和"表 4.3.1"是同一组编号的两个不同东西，只用 `JGJ231:4.3.1` 会直接撞主键。

**什么时候用**：造节点时由 `NodeBuilder` 自动调；写校验、索引、前端链接时手动调。

#### `detect_modality(text) -> str | None` — L102

**职责**：从一段正文里抽出用词等级（"应"/"宜"/"可"…），同段出现多个时取**最严格**的。

**为什么存在**：强制性条文和推荐性条文，用户必须能分清。取最严格是因为——如果一句里既有"应"又有"可"，这句话整体受"应"约束。

**什么时候用**：造条文节点时自动；做"只看强制性条款"的筛选时需要它。

#### `_target_node_id(standard_id, target_type, target_num) -> str | None` — L112

**职责**：把一个引用目标转成期望的 `node_id`。

**为什么存在**：`external_standard` 指向库外，没有 node_id，返回 `None`。这个判断让下游能区分"本库引用"和"外部标准引用"。

#### `extract_refs(text, standard_id) -> list[dict]` — L118

**职责**：用 6 条正则扫一遍文本，抽出所有引用，每条带上 `target_type / target_num / target_node_id / target_display`，`in_scope` 留 `None`。

**为什么存在**：**这是引用图的源头**。"问立杆稳定性怎么验算 → 命中 5.4.1 → 5.4.1 说按附录 C 取值 → 附录 C 被带回来"这条链路，起点就是这里抽出的边。

**什么时候用**：造任何节点时自动调。做引用覆盖率统计时手动调。

> 已知缺陷：表号带后缀时匹配不上。正文写"应符合表6.2.2的要求"，而表实际被拆成 `6.2.2-1`、`6.2.2-2`，于是产生悬空引用。这是 `eval/assess.py` 报出来的 7 个悬空引用之一，修法是找不到时回退到前缀匹配。

#### `table_agent_text(title, rows, notes=None) -> str` — L148

**职责**：把一张表格转成给检索用的**代理文本**——用扁平表头把每一行摊平成 `列名=值`。

**为什么存在**：这是解析层和检索层之间最重要的一根管子。原文是一张带合并单元格的网格，人眼一看就懂，但 BM25 和向量都读不了网格。摊平成 `类别=双排架；连墙件布置-2步3跨=1.45` 之后，问"双排架2步3跨"才能命中这张表。

**注意**：这只是**代理文本**，进 `content` 字段供检索；原始网格保留在 `body.rows` / `body.markdown_flat` 里给模型看。两者不可互换——这是 schema 三条设计原则的第三条。

**什么时候用**：解析表格节点时自动。如果你发现某张表检索不到，先看这个函数生成的文本长什么样。

### 1.3 `class NodeBuilder` — 节点工厂

**为什么要有类而不是一堆函数**：造节点需要三样上下文——标准元数据（代号/标准号/全称/版本）、当前章节位置、以及"同号冲突时给的替补编号"。这三样在整个解析过程里持续存在，用实例保存最自然。

#### `__init__(standard_id, standard_code, doc_id, version, standard_name='')` — L192

**职责**：绑定一本书的元数据。以后每次造节点，27 个字段里固定的那 6 个（`standard_id / standard_code / standard_name / doc_id / version`）自动带上。

**什么时候用**：`DocumentParser.__init__` 里建一次，全解析过程共用。

#### `set_context(chapter=None, section=None) -> NodeBuilder` — L203

**职责**：更新"当前在第几章第几节"。造节点时会写进 `chapter / section / path` 三个字段。

**为什么存在**：条文本身不带章节信息，是从上文的章标题/节标题继承的。**继承必须靠状态**，所以需要一个随时间变化的上下文。

**坑**：传 `None` 表示"只改一个、另一个不动"；要清空一节必须显式传 `section=""` 之外的处理（现在解析器是在换章时同时传 `section=None` 重置）。DB11 的条文说明区 78 个节点的 `path` 错成 `1 总则 / 7.6 拆除`，根因就在这个上下文的更新时机。

#### `_next_fallback() -> str` — L211

**职责**：给一个递增的替补编号（`seq0001`、`seq0002`…）。

**为什么存在**：两种情况会没有编号——原文漏印表号、或者同号节点撞车（比如 GB 55037 拿不到书目信息）。**没有编号也必须能存下来**，所以给个替补，同时标 `need_review`。

#### `_base(node_type, num, content, pages, bboxes, *, body=None, refs=None, ...) -> dict` — L215

**职责**：**所有节点类型的公共父函数**。27 个字段在这里一次性填好，各类型专属的 `*_node` 方法只负责准备 `content` 和 `body`。

**为什么存在**：27 个字段乘 10 种类型，如果各写一遍就是 270 处填字段，必然不一致。集中在这里，新增一种类型只需要准备两个参数。

**它是这个文件里最该读懂的一个函数**——想加字段就在这里加，一次生效。

#### 十条 `*_node` / 类型方法

| 方法 | 造什么 | 关键点 |
|---|---|---|
| `chapter_node(num, title, pages, bboxes)` L254 | 章 | 纯导航节点，`content` 只有标题 |
| `section(num, title, ...)` L258 | 节 | 同上 |
| `clause(num, content, ...)` L262 | 条 | 知识的主体 |
| `item(clause_num, item_no, content, ...)` L265 | 款/项 | `num` 记成 `4.2.1-1` 这种形式，`parent_id` 指向所属条文 |
| `table(num, title, rows, ..., tool=None, markdown_flat=None, cross_page=None)` L268 | 表 | 参数最多——因为表要同时装原始网格、扁平版、代理文本、可查询工具、跨页标记 |
| `figure(num, title, ..., image_path=None, is_vector=True)` L295 | 图 | `image_path` 是裁出来的 PNG 相对路径，前端靠它显示 |
| `formula(num, variables, ..., latex=None, linear_text=None)` L309 | 公式 | 现在只有 `linear_text`，`latex` 恒为 `None`——**这是已知短板** |
| `explanation(num, content, ..., explains=None)` L321 | 条文说明 | `explains` 指向它解释的条文号，正文和说明的双向关联从这里开始 |
| `preamble(content, ...)` L328 | 无编号内容块 | 封面、公告、前言。DB11 有 11 个，JGJ 一个没有（那本 PDF 被剥掉了前置页） |
| `appendix(letter, title, ...)` L332 | 附录标题 | 与章同级但独立成类型 |

### 1.4 校验与关联（3 个）

#### `_bbox_ok(b) -> bool` — L340

**职责**：判断坐标形态合法——接受 `[x0, top, x1, bottom]`，或同页多区域的 `[[...],[...]]`。

**为什么存在**：跨页节点的坐标是"每页一个框"，形态和单页不一样，校验必须两种都认。

#### `validate_node(node) -> list[str]` — L351

**职责**：校验单个节点，返回问题列表（空 = 通过）。

**它查什么**（这是理解字段规范最快的一条路）：字段齐不齐 → `type` 合法吗 → `level` 与 `type` 匹配吗 → `node_id` 与 `standard_id+type+num` 自洽吗 → `content` 空不空、条文是不是短得可疑 → `pages` 空不空、与 `bboxes` 等长吗 → 坐标形态合法吗 → `refs` 每条字段齐全吗 → `modality` 合法吗 → `status` 合法吗 → **`need_review` 必须带原因、`ok` 必须不带** → 有关键词必须有关键词来源（反之亦然）→ 五个列表字段确实是列表。

**什么时候用**：解析完立刻调（`run_parse.py` 就这么干）。**但要注意它只能查内部自洽**——漏掉整整一条条文，剩下的节点照样全部通过。想查漏切必须跟 PDF 原文对账，那是 `eval/assess.py` 的活。

#### `validate_all(nodes) -> dict` — L401

**职责**：批量跑 `validate_node`，汇总成 `{"total": n, "bad_count": k, "bad": [(node_id, [问题])]}`。

**什么时候用**：`run_parse.py`、`eval/assess.py`、notebook 里的例行检查。

#### `link_structure(nodes) -> list[dict]` — L413

**职责**：**一次性建立全部关系**，原地修改并返回同一个列表。四件事：

1. **父子链**——用栈维护"当前路径"，遇到层级更低的节点就压栈
2. **双向引用边**——把 `refs[i].in_scope` 定下来，同时给被引节点追加 `referenced_by`
3. **条文说明双向关联**——`explains` / `explained_by`
4. **表和图的特殊挂载**——`table/figure/formula` 不做栈操作，直接挂到"上方最近的那条"（`last_clause`）

**为什么必须单独一步、不能在造节点时做**：因为 `in_scope` 要判断"被引的节点在不在本库里"，而那是**全部节点建完之后**才知道的。所以关系只能后置统一建。

**两个实测出来的细节**（都写在注释里了）：

- 取父节点时找的是"栈里层级**小于**自己的最近一个"，不是严格的 `lv-1`。因为附录的结构是 `附录(1) → 条(3)`，中间**没有**"节"这一层，严格按 `lv-1` 会挂不上。
- `appendix` 必须和 `chapter` 一样压栈，否则附录里的条文全挂不到附录节点上。

**什么时候用**：`DocumentParser.parse()` 的最后一步。手动造节点列表时，序列化之前必须调一次。

> 已知问题：DB11 的 78 个 `explanation` 节点全部 `parent_id=None`，而 JGJ 的 50 个都正常。`eval/assess.py` 的「孤儿节点」一项就是盯这个的。

### 1.5 IO（3 个）

#### `to_jsonl(nodes, path) -> int` — L467

**职责**：一行一个 JSON 写出，自动建父目录，返回写了多少条。

**为什么用 JSONL 而不是一个大 JSON 数组**：一行一条可以流式读写，加一本规范只要 append；出问题时能直接定位到第几行。而且 git diff 友好——改一条只动一行。

#### `from_jsonl(path) -> list[dict]` — L478

**职责**：读回来。跳过空行。

**什么时候用**：索引层、评测、notebook——**所有下游都从这里进**。

#### `summary(nodes) -> dict` — L483

**职责**：产物总览——节点总数、类型分布、待复核数量与清单、引用边总数与内外分布。

**什么时候用**：解析完看一眼；`run_parse.py` 的报告开头就是它。

## 二、layout.py —— 版面层

**这层在干什么**：把 PDF 的字符坐标翻译成"版面上这是什么"。输入是 pdfplumber 的 page 对象，输出是**行、表、图、公式区**四样东西。

**这层的输入范围很窄**：它只认 page 对象里的字符、线、图元。它**不知道条文是什么**——那是 `parser.py` 的事。这个边界就是"换 OCR 只换一层"能成立的原因。

### 2.1 常量（14 个正则 + 1 张符号表）

**`PUA_SYMBOLS`** —— 私有区编码 → 正常字符的映射表（`0xF0A3 → ≤`、`0xF06A → φ`…）。

**为什么需要**：规范排版用的 Type3/Symbol 字体把数学符号塞进了 Unicode 私有区（PUA），提取出来是乱码。**这是实测撞出来的**——不修的话所有公式和"≤"全是方块。

**13 条结构正则**，每条都是在识别"版面上的某种东西"：

| 常量 | 认什么 |
|---|---|
| `CLAUSE_RE` | 条号 `4.2.1`（正文区） |
| `NOTES_CLAUSE_RE` | 条文说明区的条号（形态略不同） |
| `SECTION_RE` | 节号 `4.2` |
| `CHAPTER_RE` | 章号 `4` |
| `TABLE_TITLE_RE` | 表标题 `表4.2.1 xxx` |
| `TABLE_TITLE_NO_PREFIX_RE` | **漏印"表"字**的标题（原文缺陷，兜底用） |
| `FIGURE_TITLE_RE` | 图标题 `图5.1.4 xxx` |
| `APPENDIX_TITLE_RE` | 附录标题 `附录A xxx` |
| `APPENDIX_CLAUSE_RE` | 附录条号 `A.0.1` |
| `TOC_LINE_RE` | 目录行（**用来跳过**，不产出节点） |
| `EQNUM_RE` / `EQNUM_TAIL_RE` | 公式编号，以及"编号出现在行尾"这个特征 |
| `ITEM_RE` | 款/项编号 `1 `、`2 ` |
| `LEGEND_RE` | 图注 `1－可调托撑；2－盘扣节点…` |

### 2.2 文本修复（3 个）

#### `fix_symbols(text) -> str` — L57

**职责**：按 `PUA_SYMBOLS` 把私有区乱码换回正常字符。

**什么时候用**：所有文本入口都要过一遍——`norm_text()` 已经包含了它，所以一般不用直接调。

#### `norm_text(text, collapse_spaces=True) -> str` — L64

**职责**：`fix_symbols` + 统一换行 + 压缩行内连续空格。

**为什么叫"保守"规范化**：只做**无损**操作。不能去掉全角空格——`1 总    则` 里那些空格是排版对齐，去掉之后就分不出这是章标题了。

**这是全项目文本的第一道关口**，每个从 PDF 出来的字符串都要经过它。

#### `norm_dash(text) -> str` — L81

**职责**：把图注里的破折号归一化。

**为什么存在**：原文混用了 U+FF0D 全角减号和其他破折号——**全文只有 3 处，全在图 5.1.4 的图注里**。这种"只在一个角落出问题"的坑，只能靠逐页核对发现。

### 2.3 行重建（2 个）

#### `page_lines(page, y_tol=4.0) -> list[dict]` — L91

**职责**：把字符按纵坐标聚成行，每行带 `text / x0 / top / x1 / bottom / size`。

**为什么不用 `extract_words()`**：**中文没有空格分词**。pdfplumber 的 `extract_words` 是按空白间距切词的，中文整句会被当成一个"词"，或者被错误切开。所以必须自己按坐标聚行。

**这是整条链的起点**——下游所有东西都是从这一行行开始的。换 OCR 时，要替换的正是这个函数的输出形态。

#### `drop_running_heads(lines, page) -> list[dict]` — L126

**职责**：剔除页脚页码（纯数字 + 落在页面底部 80pt 内）。

**为什么存在**：页码会混进条文正文。**注意页码本身没丢**——它进 `pages` 字段，用来做前端高亮和溯源。

#### `repair_broken_lines(lines) -> list[dict]` — L132

**职责**：修"上一行以 `（图` 或 `（表` 结尾、下一行以编号+右括号开头"的断行。

**为什么存在**：这是实测撞出来的排印陷阱。原文里"（图 6.2.4）"被排成两行，重接之后下一行行首的 `6.2.4）` 会被误判成**新条文的条号**，凭空多出一条假条文。

### 2.4 表格还原（8 个）

#### `line_bbox(lines) -> list[float]` — L151 / `in_box(line, box, pad=2.0) -> bool` — L156

**职责**：算一组行的合并包围盒 / 判断一行是否落在某个框内。

**为什么存在**：表格和图区都要"把落在框里的行屏蔽掉"，否则表标题、表注、图题会混进条文正文。

#### `cell_text(page, bbox) -> str` — L163

**职责**：按字符坐标重建单元格文本。

**为什么这么写**：pdfplumber 给的单元格文本会把**下标拆开**——`G1+G2` 变成 `G 1 +G 2`。所以这个函数不直接用它的结果，而是把框内的字符按 x 坐标重新排序、**下标字符直接贴回主字符**。

**这是典型的"只能靠肉眼看出来"的坑**：程序跑得没错，只是每个下标前面多了个空格。

#### `_guess_header_rows(rows) -> int` — L197

**职责**：猜表头占几行。

**判据**：首行之后，**第一列连续为空**的行也算表头——因为合并表头在提取出来之后，除首行外第一列都是空的。

#### `_fill_down(rows, header_rows) -> bool` — L217

**职责**：纵向合并的单元格向下填充。

**为什么需要**：表 5.1.9 的"标准型（B型）"跨两行，只有第一行有值。不填充的话，"可调托撑"那行的型号就是空的，查表直接查不到。

#### `to_markdown(rows) -> str` — L231

**职责**：二维数组 → Markdown 表格（保留原始的多行表头）。

**什么时候用**：给人看。喂模型要用下面的 `to_markdown_flat`。

#### `_guess_units(*texts) -> str | None` — L245

**职责**：从表标题和表头里猜单位（`kN/m2`、`mm`…）。

**为什么存在**：单位常常只写在表标题或表头里，单元格里只有裸数字。不把单位提出来，`100` 到底是 kN 还是 kg 就不知道了。

#### `_union_box(boxes) -> list[float]` — L254

**职责**：算多个框的并集。用于生成表/图的"屏蔽区"。

#### `flat_header(rows, header_rows) -> list[str]` — L260

**职责**：**把多层合并表头压成单层列名**。

**为什么这是关键函数**：表格检索能不能work，全看这一步。原表可能是这样：

```
| 类别   | 连墙件布置 |        |
|        | 2步3跨     | 3步3跨  |
| 双排架 | 1.45       | 1.70    |
```

压平之后变成 `["类别", "连墙件布置-2步3跨", "连墙件布置-3步3跨"]`，于是"双排架 + 2步3跨"这个组合能被表达成 `类别=双排架；连墙件布置-2步3跨=1.45`——**问"双排架2步3跨的系数"才可能命中**。

不压平的话，表头是"类别 / 连墙件布置 / 空"，值行是"双排架 / 1.45 / 1.70"，语义完全丢失。

#### `_clean_header_cell(cell) -> str` — L297

**职责**：表头单元格清洗。多行合并的 `" / "` 直接相连（`"承载力设计值 / （kN）"` → `"承载力设计值（kN）"`）。

#### `to_markdown_flat(rows, header_rows, flat) -> str` — L307

**职责**：扁平表头版的 Markdown：单行表头 + 数据行。

**什么时候用**：**喂 LLM 用这个，别用带合并表头的原表**。模型对合并表头的理解很不稳定。

#### `real_tables(page, lines) -> list[dict]` — L321

**职责**：抽表格 + 过滤假阳性 + 还原表标题、表注、表头行数、纵向填充。

**它做四件事**：

1. **过滤假阳性**——矢量图会被 `find_tables()` 误判成表格。判据：区域内文字单元格少于 2 个、或字符数少于 6 个 → 不是真表。
2. **找表标题**——在表格上方 50pt 内找，优先带"表"字的，找不到用备用判据（兜底原文漏印"表"字的情况，找到后**补回"表"字**）。
3. **抽表注**——表格下方 130pt 内的 `注：` 开头的行，遇到下一条/节/表/图标题就停。
4. **算屏蔽区 `block_bbox`**——表体 + 表标题 + 表注的并集。**不盖住标题和表注，它们会被当成正文吸进条文**。

**什么时候用**：解析时每页自动调。调试表格问题时从这里入手。

#### `merge_cross_page_tables(prev, cur, prev_no, cur_no) -> list[dict]` — L388

**职责**：把跨页的表头（或表体前半）和本页的表体合成一张逻辑表。

**判据**（四条同时满足）：上页表贴到页底（`bottom > 720`）+ 本页表顶在页首（`top < 120`）+ 横向对齐 + **本页这张表自己没有标题行**。

**最后一条是关键**：表 C.0.1 在第 36 页结束、表 C.0.2 在第 37 页另起且**带自己的标题**。少了这条判断，两张表会被误并成一张 54 行的大表。

**两种形态必须分开处理**（这是踩过的坑）：

- 上页页尾只有 1~3 行 → 那是**表头**，并到本页表体前面
- 上页页尾有几十行 → 那是**表体的前半**，整体行拼接

只处理第一种的话，DB11 表 A.0.1 会变成"113 行里 108 行是表头"。

### 2.5 图区（3 个）

#### `graphic_clusters(page, gap=14.0, min_w=60.0, min_h=60.0) -> list[list[float]]` — L429

**职责**：把邻近的图元聚成图区。

**为什么三类图元都要收**：`curves`/`lines` 是矢量图（大部分图是这种），`images` 是位图。**只收矢量会整张漏掉位图**——实测第 47 页的图 3 就是位图。

**面积超过整页 80% 的图元当背景跳过**，否则整页会被当成一张图。

#### `group_figures(clusters, lines, table_boxes) -> list[dict]` — L459

**职责**：按图题把多个子图合并成一张图，并把图题、图注、子图标签一并归属。

**为什么需要合并**：一张图可能由左右两个子图组成，图元聚类会把它拆成两块。图题只有一个，所以要按"图题上方的块"归组。

**两个坐标要分清**：`bbox`（含图题与图注）和 `art_bbox`（只有图像本体）。**节点用 `bbox`**——不盖住图题，图题会被当成正文。

#### `crop_png(page, bbox, path, resolution=200, pad=4.0) -> str` — L502

**职责**：按坐标裁图存 PNG，自动建目录，外扩 4pt 留白。

**为什么这么实现**：pdfplumber 的 `PageImage` **没有** `crop()` 方法，所以要先在 page 上裁、再渲染成图。

**什么时候用**：解析图节点时自动。单独想截某项内容时可以直接调。

### 2.6 公式区（1 个）

#### `formula_regions(lines, exclude=()) -> list[dict]` — L513

**职责**：识别公式区，返回 `equation_id` + `bbox` + `linear_text`。

**三条判据缺一不可**：

1. **不含中文**——含中文的是叙述行（"不组合风荷载时："）
2. **行宽 < 300pt**——正文行宽约 450pt，公式居中且窄
3. **公式编号在行尾**——"…按本标准式（5.3.3-1）计算。" 是**引用**，不是公式本身

**为什么必须独立成节点**：线性化会丢分式结构。式(4.4.3) 本来是 γ₀S ≤ R/γ_R，线性化后变成 `R γ0S≤ γR`——符号顺序被拍平了。所以公式的核心价值在截图 + 变量表，不在那行文本。

**已知短板**：现在只存 `linear_text`，`latex` 恒为 `None`，所以所有公式节点都标了 `formula_linear_only`。这是写论文前必须补的一项。

## 三、parser.py —— 解析层

**这层在干什么**：把"版面元素"变成"条文树"。**切分真正发生在这里**——版面层只告诉你"这里有一行字"，解析层才知道"这一行是第 4.2.1 条的开始"。

**它依赖前两层**：用 `layout` 认元素，用 `schema.NodeBuilder` 造节点。

### 3.1 `class DocumentParser` —— 主解析器

#### `__init__(pdf_path, standard_id, standard_code, doc_id, version, *, standard_name='', page_offset=0, figure_dir=None, y_tol=6.0, verbose=False)` — L38

**职责**：绑定一本 PDF 和它的元数据，建一个 `NodeBuilder` 备用。

**三个参数最容易搞错**：
- `standard_id` —— 进 `node_id` 前缀。**两本规范用同一个 id，主键会全部撞车**，混库和引用图直接乱
- `page_offset` —— PDF 第 1 页对应的原书页码减 1。JGJ/DB11 是 `0`（页脚就印着 1），GB 55037 是 `4`（PDF 第 5 页才是书上第 1 页）。**传错网页高亮会整体偏移**
- `figure_dir` —— 裁图输出目录。**传 `None` 就不裁图**，`image_path` 全是空

#### `_collect(pdf) -> list[dict]` — L52

**职责**：逐页采集，返回每页的 `lines / tables / figures / skip / blocked / notes / body_size`。**这是全文最重的一个采集函数**。

它按顺序做五件事：

1. `page_lines` 聚行 → `drop_running_heads` 去页脚 → `repair_broken_lines` 修断行
2. `real_tables` 抽表 + `merge_cross_page_tables` 合并跨页表
3. `graphic_clusters` + `group_figures` 定位图
4. 算出 `skip` 集合（表标题、表注、图题、图注的文本）和 `blocked` 区（它们的坐标框）
5. 判断本页属不属于条文说明区（`notes`），并算正文字号中位数（`body_size`）

**第 4 步是理解整个解析器的钥匙**：`skip` 和 `blocked` 就是"这些内容不是正文，别吸进条文里"的名单。表标题、表注、图题、图注四样东西，如果不屏蔽，全会被当成条文正文。

#### `_segments(pg) -> list[dict]` — L111

**职责**：把一页的行切成 章/节/条 片段，被屏蔽区打断的片段自动断开。

**逻辑**：逐行扫描 → 命中 `blocked` 或 `skip` 就断开当前片段 → 判断这行是不是标题（或条文起点）→ 是就开新片段，不是就追加到当前片段。**没归属的行开一个 `continuation` 片段**。

**为什么片段要能断开又续上**：条文被表格打断时，前后两段属于同一条——断开的片段留给 `_assemble` 去合并。

#### `_elements(pages) -> list[dict]` — L149

**职责**：把每页的片段、表、图**拉平成一个序列，并按（页号，纵坐标）排序**。

**为什么必须排序**：`_assemble` 依赖"表挂到它上方最近的条"这个规则，那要求序列严格按版面顺序。排序键是 `(page_index, top)`。

#### `_crop(page, fig) -> str | None` — L161

**职责**：裁出图并返回相对项目根的路径。

**一个细节**：`image_path` 存成 **POSIX 风格**（`output/…/figures/x.png`，用 `/` 不用 `\`），跨平台和前端引用都省事。

#### `_emit_formulas(nodes, lines, page) -> None` — L173

**职责**：从一组行里抽公式节点，`status` 一律标 `need_review` + `formula_linear_only`。

**为什么所有公式都标待复核**：因为它只存了线性文本，不存结构化公式——**解析器自己知道这里不完整**，所以主动标出来。这是 `status` 字段的用法示范：不是"成功/失败"，是"确定/待人工确认"。

#### `_consume_items(nodes, lines, clause_num, page, state, *, require_list, seg_text='') -> None` — L186

**职责**：切款/项。

**两个关键约束**（都是实测撞出来的）：

1. **款号必须从 1 开始且连续**。不连续就不认——否则引用标准名录里那些"9 《…》"的行会被误判成第 9 款。
2. **跨页时编号要能跨段连续**。所以 `state` 在条文之间传递（`next` = 下一个期望的款号）。

**`require_list` 的作用**：条文首段要求正文含"下列"或"应包括"才启用切款；续接片段（`require_list=False`）要求本条**已经至少有一款**才继续编号。

> 注意：同文件里还有个 `_split_items()`（L485），**已经没人调用了**——它被这个 `_consume_items` 取代，但没删掉。读代码时别被它带偏。

#### `_assemble(els) -> list[dict]` — L214 ★

**职责**：**全文最长的一个函数（128 行），也是切分的核心。** 把排好序的元素流，一条条变成节点。

它的主循环按 `el["kind"]` 分四路：

**表** → 跳过已被并入下一页的碎片（`merged_into_next`）→ 算扁平表头 → 试着工具化 → 造表节点。

> 两处细节值得记：表号可能识别不出来（原文漏印"表"字、或是跨页续表的碎片），这类表**内容是真知识不能丢**，但必须标 `need_review`；同时**不能生成 `表None` 这种垃圾关键词**——它会让混库建索引直接崩。

**图** → 裁图 + 造图节点。

**章 / 节 / 附录** → 更新 `NodeBuilder` 的章节上下文，造导航节点，`current` 清空。
　　特例：条文说明区的章/节**只更新上下文、不造节点**——它们会和正文章节重号，而且作为导航没有价值。

**条 / 续接** → 这是最核心的分支：

- 如果新条文的条号**等于当前条的条号** → 说明条文被表格/插图打断后又续上了，调 `_merge_continuation` 并回，标 `split_by_table`
- 否则起新条节点 → 重置款的计数状态 → 切款 → 抽公式
- **没有条号开头的片段** → 视为上一条的跨页续接，并回并标 `cross_page_clause`（跨页）或 `split_by_table`（同页）
- **如果连"上一条"都没有** → 造 `preamble` 节点（封面/公告/前言）

**为什么这一段这么长还这么绕**：因为它就是被 16 类排印陷阱一轮轮逼出来的。每一段 `if` 背后都是一次实测翻车。这也是为什么这个文件最难读——**它不是设计出来的，是长出来的**。

#### `parse(max_pages=None) -> list[dict]` — L344

**职责**：入口，串起全部五步：

```
_collect（逐页采集）
  → _elements（拉平排序）
    → _assemble（切分，裁图在这里完成，所以此时 pdf 必须还开着）
关闭 PDF
  → link_structure（建父子与引用边）
    → _refine_formula_variables（重分配公式变量）
      → _link_explanations（连条文说明）
```

**顺序不可换的两个地方**：
- `_assemble` 必须在 `with pdfplumber.open(...)` **块内**——因为它要裁图
- `link_structure` 必须在**全部节点建完之后**——因为 `in_scope` 要判断引用目标在不在库里

`max_pages` 只解析前 N 页，用于快速试验（当初的 POC 就是靠它只跑两页）。

#### `_link_explanations(nodes) -> None` — L356

**职责**：把条文说明挂到它解释的条文上，双向。

**为什么重要**：这是"**这条规定的依据是什么**"唯一能回答的来源。规范里约三分之一的条文有官方说明，其余没有。

**一个不能省的细节**：一条说明可能覆盖多条条文（`7.4.1~7.4.3`、`7.4.11、7.4.12`），**全都要连上**——只连第一条的话，问后面几条就查不到依据了。

#### `_refine_formula_variables(nodes) -> None` — L377

**职责**：用**条文的完整正文**重新扫一遍"式中："段落，重新分配变量给公式。

**为什么必须在最后做这一步**（两个原因）：

1. 一条文里的多个公式常**共用同一个"式中："段落**（如 5.3.3-1 与 5.3.3-2）
2. "式中"段落会**跨页**，在公式所在的片段里取不全

**分配策略**：只有一段 → 所有公式共用；段数与公式数相等 → 一一对应；**数量对不上就不冒险映射**（宁可缺，不要错）。

### 3.2 模块级辅助函数（14 个）

#### `_body_size(page) -> float` — L406

**职责**：算页内正文字号（中位数）。

**为什么用中位数不用平均值**：标题字号大、页脚字号小，平均值会被拉偏。中位数代表"大多数行"。

**它是区分标题和正文的基准**——下面 `_heading_kind` 全靠它。

#### `_heading_kind(line, body_size) -> str | None` — L412

**职责**：判定一行是章标题、节标题，还是都不是。

**判据**：字号明显大于正文 + 编号形态对得上。

**一个必须做的排除**：**条号要先排除掉**。条号也是"数字开头"，字号有时也略大，不排除的话 `4.2.1` 会被当成节标题。

#### `_split_heading(text) -> tuple[str, str]` — L438

**职责**：把 `"4.2 荷载标准值"` 拆成 `("4.2", "荷载标准值")`。

#### `_clause_num(text) -> str` — L448

**职责**：从行首取条号。

**为什么单独一个函数**：条文号有**两种形态**——正文是 `5.3.3`，附录是 `A.0.1`。两种都要认，所以统一在这里处理。

#### `_explanation_targets(text) -> list[str]` — L462

**职责**：从条文说明的开头抽它覆盖的条文号。

**实测四种写法都要认**：

| 写法 | 例子 | 处理 |
|---|---|---|
| 单条 | `1.0.1 本条是…` | 直接取 |
| 区间 | `7.4.1~7.4.3 明确了…` | **展开成 3 条** |
| 列举 | `7.4.11、7.4.12 明确…` | 逐个取 |
| 列举 | `5.1.2、5.1.3 给出了…` | 逐个取 |

**只看开头 60 字、遇到句号或换行就停**——避免把正文里提到的其他条号也抽进来。

#### `_split_items(seg) -> list[tuple[str, list[dict]]]` — L485 ⚠

**职责**：切款/项。

**注意：这个函数已经没人调用了**，`DocumentParser._consume_items` 取代了它。保留在文件里属于历史遗留。读代码时可以跳过。

#### `_variables_from(lines, formula) -> list[dict]` — L509

**职责**：从公式区之后的"式中："段落里抽变量表。

**为什么符号能读对**：下标在行重建阶段（`layout.cell_text`）已经贴回主字符了，所以这里拿到的是 `G1` 而不是 `G 1`。

#### `_parse_vars(blob) -> list[dict]` — L528

**职责**：从一段"式中"文本里抽变量，形态是 `符号——释义（单位）`。

#### `_where_blocks(clause_text) -> list[list[dict]]` — L541

**职责**：按出现顺序，抽出一个条文里的**所有**"式中："段落。

**为什么是"所有"**：一条文可能有多个公式、多段"式中"，数量要和公式数对上才能正确分配。

#### `_formula_content(num, variables) -> str` — L551

**职责**：生成公式的**检索代理文本** = 式号 + 变量语义。

**为什么不用公式本体**：`γ0S≤R/γR` 这种符号串对 BM25 和 embedding 都没有信息量。**变量释义才是能被检索到的东西**——问"稳定系数怎么算"，命中的依据是"φ——轴心受压构件的稳定系数"这句释义，不是那个希腊字母。

#### `_structural_keywords(num, section) -> list[str]` — L559

**职责**：给条文生成"结构型关键词"——就是编号本身（`5.4.2`、`第5.4.2条`）。

**为什么专门加编号当关键词**：**BM25 对编号的精确匹配远强于向量**。有人直接问"5.4.2 说了什么"时，靠的就是这个。

#### `_merge_continuation(node, page_no, bbox, text) -> None` — L567

**职责**：把跨页/被表格打断的续接文本并回上一条文，同时合并页码与坐标。

**为什么要合并坐标**：前端高亮要框住**整条条文**，而条文横跨两页，所以 `bboxes` 要变成两个框。

#### `_append_line(node, page_no, line) -> None` — L574

**职责**：把一行续接到已有节点（款/项的跨页续写）。

**和 `_merge_continuation` 的区别**：这个接的是**单行**，那个接的是**整段**。

#### `_merge_page_bbox(node, page_no, bbox) -> None` — L581

**职责**：把新页的坐标并进节点的 `pages` / `bboxes`。

## 四、tables.py —— 附表工具化层

**这层在干什么**：把"查值表"转成**可精确查询的结构**。

**为什么需要这一层**：一张稳定系数表有 251 个值、2000 多字。把它整段喂给模型，让它在数字流里挑对的那个——**成功率远低于按参数精确查表**。所以改成：内容不进上下文，只留一个"表头 + 参数 + 示例值"的短代理文本，精确值走 `lookup()` 查。

**这层的输出是两样东西**：解析时写进 `node.body.tool`，索引时由 `TableTools` 载入内存供生成层调用。

### 4.1 常量（2 个）

**`_PLACEHOLDERS`** —— 空值占位符（`-`、`/`、`—`…），`_clean()` 会把它们清成空串。
**为什么需要**：原表里用短横线表示"无此项"，但程序分不清"无此项"和"值就是一个短横线"。

**`_KEY_HINTS = ("型号", "编号", "序号", "代码", "标识")`** —— 天然适合当行键的列名。

**注意它故意不含"名称/类别"**：那些是**分组列**（"立杆"跨十几行），当键会让行互相覆盖。

### 4.2 内部函数（7 个）

#### `_clean(cell) -> str` — L33

**职责**：单元格文本清洗——去首尾空白，把占位符清成空串。

#### `_drop_constant_columns(header, body) -> list[int]` — L38

**职责**：找出"整列恒定的废列"，返回列号。

**三种情况都算废列**：

1. **这一列没有表头** —— pdfplumber 多切出来的列。实测 DB11 表 A.0.1 的 6 个数据列被抽成 **11 列**，不剔除会让属性错位（型号 `B-LG-3000` 会串到别人的单重上去）
2. **整列全空**
3. **整列同值** —— 原表用重复词组表现合并表头。实测 JGJ 表 A.0.1 第 2 列整列都是"地面粗糙度 μz 类别"，没有任何信息量，留着会让代理文本变成"地面粗糙度…=地面粗糙度…"这种废话

#### `_pick_key_column(header, body) -> int` — L64

**职责**：选一列作行键。

**为什么不能默认用第 1 列**：第 1 列常常是**分组列**而不是标识列。实测 DB11 表 A.0.1 第 1 列是"名称"（立杆/水平杆…，113 行里只有 13 个唯一值），拿它当键会让后面的行互相覆盖。真正能唯一标识构配件的是"**型号**"列（`Z-LG-500`…，74 个唯一值）。

**规则**：列名命中 `_KEY_HINTS` 的优先；否则取**唯一值最多**的那一列。

#### `classify_table(title, rows) -> str` — L89

**职责**：判断表类型，返回 `template` / `lookup` / `grid`。

**三类**：
- `template` —— 表单模板（记录表、验收表），**不进检索**
- `lookup` —— 查值表，**要工具化**
- `grid` —— 普通表格，保持原样

**判据只看结构特征、不看格数**：
- 标题含"记录表/验收记录/验收表" → `template`
- 行数 < 3 或行键 < 3 个 → `grid`
- **行键里 80% 以上能解析成数值** → `lookup`
- **行数 ≥ 20 的大规格表**也算 `lookup`（按键找行）
- 其余 → `grid`

**为什么强调"不看格数"**：格数会把小表误判成大表。

#### `_digit_grid(header, body) -> dict | None` — L116

**职责**：识别"**十位为行、个位为列**"的数字矩阵——就是 JGJ 表 C.0.1 / C.0.2 的稳定系数表。

**为什么必须专门处理**：那种表的排法是行首是 `120`、列头是 `0 1 2 … 9`，值要**拼**起来才是 `λ=125`。不拼的话**永远只能查到整十数**，问 λ=100 能答，问 λ=105 就查不到。

**判据**：列头全是单个数字 + 行键全是整数 + 拼出来的记录数 ≥ 20。

#### `build_tool(title, rows, header_rows=1, min_chars=800, orig_chars=0) -> dict | None` — L149

**职责**：**这一层的主函数**。把一张表转成可查询结构；不是查值表、或本来就不长的话返回 `None`。

**流程**：长度门槛 → 分类 → 剔废列 → 试数字矩阵 → 否则通用行查值表（选键列、其余作属性）。

**长度门槛为什么要**：用**原代理文本的长度**判断，不是估算记录大小——因为它才是真正要省的那个量。原文本不到 800 字的表（如 JGJ 表 B.0.1 那种 129 字的小常量表）**保持原样更好**——工具化反而丢掉了"一眼看全"的优势。

**同名键会合并属性**（`records.setdefault(key, {}).update(item)`）——这是为纵向合并单元格准备的。

#### `brief_content(title, tool, sample=4) -> str` — L201

**职责**：生成查值表的**短代理文本** = 表头 + 参数 + 几个示例值。

**为什么要放示例值**：「不只是好看」——常见取值直接出现在材料里，模型**不查表也能答对**；精确值再走查表工具。等于给模型一个双保险。

### 4.3 `class TableTools` —— 运行时查表容器

#### `__init__(tools=None)` — L232 / `from_nodes(nodes)` — L236

**职责**：从节点列表里把带 `body.tool` 的表挑出来，建成 `{标准号:表号 → tool}` 的字典。

**为什么直接从 nodes 建**：不需要额外存一份——工具结构就存在节点里，索引时顺手载入。

#### `lookup(standard_id, table_num, key) -> dict | None` — L248

**职责**：按参数查值。

**两道防噪音闸**（都是实测撞出来的）：

1. **数字键先精确匹配，再退到最接近的键**——因为像 λ=105 这种值在表里可能不存在，退到最近的一档比直接失败有用
2. **超出表范围太多就直接不认**：`target < 最小值-5` 或 `> 最大值+5` 就返回 `None`。**实测踩过**：型号 `Z-LG-3000` 里的 `3000` 会被当成长细比就近命中 λ=250，给出一条完全无关的查表结果

**返回**：`{key, value, exact, title, key_name, value_name, columns, node_id}`。`exact=False` 表示取的是近似档——答案里会标注"表中无此精确值，取最接近的一档"。

#### `describe() -> str` — L280

**职责**：列出手里有哪些查值表。调试用。

> 全项目扫描发现它没有被任何地方调用——属于备用的诊断工具。

## 五、index.py —— 检索层

**这层在干什么**：给一个问题，从几百个节点里挑出该交给模型的那些。

**关键前提**：**它完全不读 PDF**。输入只有 `nodes.jsonl`。所以改了 `parser.py` 必须重建索引——索引看到的是上次解析写下的快照。

**为什么用三路而不是一路**：单一路径都有明确短板，三路互补：

| 路子 | 强项 | 短板 |
|---|---|---|
| BM25 | 精确——问 `5.4.2` 就找到 5.4.2 | 换个说法就找不到 |
| 向量 | 容错——问"立杆稳定性"能命中"稳定系数" | 编号、型号这类串它反而会跑偏 |
| 引用图 | 答案不在命中的那条里时能带出来 | 只有引用关系才行 |

### 5.1 常量（7 个）

| 常量 | 作用 |
|---|---|
| `_STRUCT_PATTERNS` | 结构标识符的模式：条号、表号、图号、数值+单位、英文、希腊字母。分词时**整段抽出、不切开** |
| `_CJK_RE` | 判断是不是中日韩字符，用于中英混排处的切分 |
| `VECTOR_TYPES` | **哪些类型进向量库**——款、章标题不进。理由见 `build_index` |
| `REF_KINDS` | 哪几种边算"跨章引用"，供闭包扩展分轮取用 |
| `_TYPED_MENTIONS` | 带类型前缀的提及（"表5.1.9""第5.4.2条"） |
| `_BARE_CLAUSE` | 光秃秃的条号（"5.4.2"） |
| `DOMAIN_SYNONYMS` | 领域同义词表：盘扣架 → 承插型盘扣式钢管脚手架；步距 → lift height … |

### 5.2 `tokenize(text) -> list[str]` — L51

**职责**：**混合分词**。

**为什么不能直接用通用分词器**：规范里全是 `2步3跨`、`Q355`、`φ48.3`、`5.4.2` 这种词。通用分词器会把它们切碎——`2步3跨` 切成 `2`、`步`、`3`、`跨` 之后，BM25 就再也匹配不到这个术语了。

**策略**：先把结构标识符**整段抽出**（不切），剩下的中文再按二元组切。

**什么时候会改它**：检索不到某个术语时，先看它被切成了什么。

### 5.3 `class BM25Index` — L85

#### `__init__(docs, k1=1.5, b=0.75)` — L91

**职责**：建索引。`docs = [(doc_id, content, keywords_text)]`。

**参数是教科书默认值**（k1 控制词频饱和、b 控制长度归一化）。**语料只有几百条，直接内存里算**——不需要 Elasticsearch 那一套。

#### `search(query, top_k=10) -> list[tuple[str, float]]` — L108

**职责**：返回 `[(node_id, 分数)]`，按分数降序。

### 5.4 向量（3 个类）

#### `class Embedder` — L130

**职责**：调 LM Studio 的 OpenAI 兼容 embedding 接口，**带磁盘缓存**。

**缓存是按文本 sha1 做的 key**（`_key()` L145）——这个设计有个实际好处：**搬目录、改文件名都不会让缓存失效**，因为 key 只跟文本内容有关。整个项目搬迁时索引能秒级重建，靠的就是这一点。

**`available()`** L148：探一下服务在不在。
**`embed(texts)`** L155：**每 16 条一批**发请求，避免单次请求过大。

**服务不可用时的报错写得比较啰嗦**（提示启动 LM Studio 或改用 `HashingEmbedder`）——因为这是最常见的翻车点。

#### `class HashingEmbedder` — L178

**职责**：确定性哈希向量（字符二元组 → 512 维），**不依赖任何外部服务**。

**⚠ 关键警告写在 docstring 里：只能用来验证管道连通性，不能用于评估。** 它没有语义能力，用它算出来的召回率没有意义。

#### `class VectorIndex` — L201

**职责**：余弦相似度**暴力检索**。

**为什么不用 FAISS / Milvus**：语料只有几百到几千条。暴力算比建索引库**更快、更透明、更好调试**——而且没有额外依赖。等到几万条再换也不迟。

### 5.5 `class TableStore` — L224

**职责**：表格结构化库（SQLite）。

**为什么用 SQLite**：让"2步3跨布置时双排架系数是多少"这类问题走**精确取值**，而不是在文本里模糊匹配。

**`add_table(node)`** L248：索引时把表行灌进去。
**`find_rows(phrase, top_k=5)`** L266：按行文本做朴素匹配。

**已知不足**（注释里写明了）：演示够用，换成 FTS5 或接 BM25 都很容易。

### 5.6 `class RefGraph` — L283

**职责**：关系图，节点 = `node_id`，**两种边**：

- **引用边** —— `refs` 抽出来的（跨章、跨附录）
- **父子边（contains）** —— `parent_id` / `child_ids`

**为什么父子边也必须进图**：只存引用边的话，"命中一张表、要把它的所属条文带回来"就做不到。这是链路能跑通的前提。

**`neighbors(node_id, hops=1, successors_only=False, kinds=None)`** L304：取邻居。`successors_only=True` 时只向下走（引用边 + 父子边）。
**`stats()`** L334：节点数、边数。健康检查用。

### 5.7 查询改造（2 个函数）

#### `mentioned_ids(query, standard_id) -> set[str]` — L358

**职责**：从问题里抽出**被显式点名**的节点 id（"表5.1.9"、"5.4.2"、"图5.1.4"）。

**为什么要这一步**：编号查询**不能交给向量**。向量会觉得"5.4.2"和"5.4.3"很像——但用户问的是确定的一条。

#### `expand_query(query) -> str` — L400

**职责**：查询侧同义词扩展，把口语词追加成规范用词。

**为什么放在查询侧而不是索引侧**：索引侧扩展会让每个节点都变长、拖慢检索；查询侧只处理一次，代价可以忽略。

**注意**：扩展只用于检索，**原始 query 仍然保留供展示**——用户不该看到自己的问题被改了。

### 5.8 `class HybridRetriever` — L413 ★

**这层最核心的类。**

#### `search(query, top_k=10, alpha=0.5, pool=30, expand_hops=0, mention_boost=0.05) -> list[dict]` — L430

**职责**：三路检索 + 融合 + 图扩展。

**五步**：

**① 两路各取 `pool=30` 个候选**（BM25 + 向量）。

**② RRF 融合**：
```
score = alpha/(60 + bm25_rank) + (1-alpha)/(60 + vec_rank)
```

**为什么用 RRF 而不是加权分数**：BM25 的分数无上界（实测见过 43 分），余弦在 0~1。直接相加没有意义，归一化又会随语料变化。**RRF 只看排名**——稳定，而且几乎不用调参。`alpha` 就是两路的权重旋钮。

**③ 显式标识符硬加权**：问题里点名了表/条/图，就把它顶上来。

**为什么放在 RRF 之后**：这一步等于宣布"**硬规则优先于相似度**"。用户明确说了"表5.1.9"，任何相似度都不该把它挤下去。

**④ 引用闭包扩展**（`expand_hops > 0`）——**这里有两个实测撞出来的约束**：

- **种子不能是节/章**。它们链接着整节的所有条文，从它们扩展会把上下文瞬间淹掉。所以只从"内容型"节点（条/款/表/图/公式）出发。
- **逐种子轮转取，每个种子每轮最多取 1 个**。**实测踩过**：5.4.1 一条就带 4 款 + 3 公式 + 1 表，顺序取会把 6 个预算占满，真正需要的附录 C（由 5.3.3 引用）反而拿不回来。

**⑤ 分两轮取**：第一轮走**跨章引用**（`REF_KINDS`，预算 5）——这才是闭包的价值所在；第二轮才补父子边（`contains`，预算 4，主要是子表/子公式/款）。

**顺序反了会怎样**：父子边数量远多于引用边，先取父子就会把预算吃光，附录永远带不回来。

### 5.9 `class IndexBundle` — L519

**职责**：一次构建、多处使用。把 BM25 / 向量 / 表格库 / 引用图 / 混合检索**打成一个包**。

**为什么要打包**：这些东西共享同一份节点数据，分开传参太啰嗦。`app.py` 和 notebook 都只持有一个 `bundle`。

### 5.10 组装（2 个函数）

#### `_index_text(node) -> str` — L534

**职责**：决定一个节点**进索引的正文**是什么。

**规则**：表格用检索代理文本；条文用原文。

**什么时候会改它**：发现某类节点检索不到时，先看这里取了什么文本。

#### `build_index(nodes, out_dir, embedder=None) -> IndexBundle` — L539

**职责**：建全部索引。

**三件事值得记**：

1. **`embedder=None` 时自动尝试 LM Studio，失败退化为哈希向量**——这样没启动模型也能把管道跑通
2. **只有 `VECTOR_TYPES` 里的类型进向量库**。"款"（`item`）和章标题不进——款的内容是条文的一部分，重复进向量库只会挤占名额
3. **同时落两个文件**：`embeddings.json`（向量缓存）和 `tables.db`（表格库）

**输出产物**：`out_dir/embeddings.json` + `out_dir/tables.db`。这两个都在 `.gitignore` 里，属于**可重建的缓存**。

## 六、generate.py —— 生成层

**这层在干什么**：把检索到的候选，变成**有依据、可追溯、不编造**的答案。

**三条约束决定了这一层的全部设计**（文件开头的注释就是这么写的）：

1. 施工规范问答**必须给法源**——所以提示词强制标注条号，生成后还要回查
2. 材料里没有的**不能编**——所以要显式拒答，而不是"尽力回答"
3. 命中款/公式时用户要看到**完整条文**——所以要做父子回填

### 6.1 常量（4 个）

| 常量 | 作用 |
|---|---|
| `CITE_PATTERNS` | 从**答案**里抽引用的正则（和 `schema._REF_PATTERNS` 保持一致的形态） |
| `REFUSAL_MARKERS` | 拒答的标志短语，用来判断模型是不是拒答了 |
| `_NUM_CAND` | 从问题里抽数字候选（当表格的键用） |
| `_MODEL_CAND` | 从问题里抽型号串（`Z-LG-3000` 这种） |

### 6.2 渲染（4 个函数）

#### `grams(s) -> set` — L47

**职责**：把一个字符串切成字符二元组集合（`"双排架"` → `{"双排", "排架"}`）。

**为什么用二元组**：中文没有空格分词，二元组是**最省事又不丢信息的相似度单位**。它的开销只在判断"表标题和问题有没有关系"这一处，不需要更精细的分词。

**什么时候会注意到它**：`_title_overlap` 的判据（重叠 < 2 就跳过查表）就是拿它的结果比出来的。如果发现某张该查的表没被查，可以调这个阈值。

#### `_title_overlap(title, question) -> int` — L39

**职责**：算表标题和问题的二元组重叠数。

**为什么需要**：判断"这张表跟问题到底有没有关系"。**防止"一个数字匹配所有表"**——截断在 `_probe_table` 里用（重叠 < 2 就跳过）。

#### `build_system_prompt(standards, multi) -> str` — L53

**职责**：按知识库里的规范**动态生成**系统提示词。

**为什么动态**：单本库和混库的提示词不一样——混库时必须要求"每条结论标明出自哪一本"，还要约定冲突时的表达方式。

#### `_label(node) -> str` — L85

**职责**：给材料块一个**可被引用的编号标签**（如 `【材料3】JGJ/T 231-2021 表5.4.1`）。

**为什么需要**：模型要能"指着材料说话"，否则引用回查没法做。

#### `render_block(node, with_standard=False) -> str` — L106

**职责**：把一个节点渲染成给 LLM 的材料块。

**两条规则**：表格用**扁平表头版**（不用带合并表头的原表）；公式**带变量表**（因为本体符号没意义）。

### 6.3 `class Answerer` —— 问答器

#### `__init__(bundle, llm_base=..., model=..., temperature=0.1, timeout=900, max_tokens=1200, reasoning_effort='none')` — L146

**职责**：绑定索引包和本地模型。

**`temperature=0.1`** —— 规范问答要的是稳定复现，不要"创造性"。

**`reasoning_effort='none'`** —— **这是实测调出来的关键参数**。本地 27B 默认开思考模式，首字要 26 秒；关掉之后降到 3 秒，而答案质量没变。取值必须是 `"none"`，写 `"off"` 会返回 400。

#### `_key_candidates(question) -> list[str]` — L176

**职责**：从问题里抽出可能的表格键——**先型号串（更具体），再数字（长的优先）**。

**一个必要的过滤**：去掉 4 位、以 `19`/`20` 开头的数字——**那是年份或规范号**（GB 50009、2021），不是表格的键。

#### `_probe_table(node, question) -> str | None` — L189

**职责**：命中的表若是查值表，**替模型把值查好**，作为一行短材料附在表后面。

**为什么不直接让模型读整张表**：一张稳定系数表有 251 个值、2000 多字。模型在数字流里挑对的那个，概率远低于按参数精确查表。

**三道闸**（缺一不可）：
1. 不是查值表 → 跳过
2. **表标题里的钢材牌号要和问题一致** —— 问 Q235 时别把 Q355 的表也查出来，否则两张表的值一起进材料，模型有拿错的风险
3. **标题与问题的语义重叠 < 2 → 跳过** —— 防止"一个数字匹配所有表"

#### `_direct_lookup(question, exclude=()) -> list[dict]` — L223

**职责**：直接对所有查值表试键，**完全不依赖检索命中**。

**为什么需要这一步**：型号（`Z-LG-3000`）、参数（`λ=100`）这类串**对向量检索来说信息量太低**，表往往根本不会被召回——但它恰恰是唯一能回答问题的依据。而查值是精确匹配，误命中风险远低于向量相似度，**所以可以放心全表扫一遍**。

**这是这个项目里一个不显然但很重要的设计**：检索负责"找回相关的"，但**关键依据不能完全交给检索**。

#### `build_context(hits, max_chars=9000, max_blocks=10, question='') -> list[dict]` — L262 ★

**职责**：上下文组装——父子回填 + 去重 + 排序 + 预算控制。

**四步**：

**① 过滤 + 去重**：节/章是导航节点，正文是空的，喂进去只会拖慢首字、不提供任何依据，直接丢掉。

**② 父子回填**：命中款/表/图/公式时，把**所属条文一并带上**——因为用户要看完整条文。

**③ 两段式填充**（**这里踩过一个很值得记的坑**）：

先把"直接命中"（`score > 0`）按类型排进去，**再**补"图扩展带出来的"（零分）。如果混在一起按类型排，**零分的扩展节点会靠类型顺序把高分的表挤出去**——实测问"可调托撑承载力"，表 5.1.9 被 5 条零分扩展条文挤掉，模型只能回答"材料中未规定"。

**④ 分数比例过滤**：只保留与最高分同量级（≥ 0.5×top）的直接命中。

**关于块数的实测数据**（注释里记着）：关掉思考模式后，6 块→2.4s、10 块→3.6s、20 块→4.2s，**几乎不影响首字**。所以默认给 10 块。早期"10 块材料首字 26.7s"的结论是在 reasoning 开着的情况下测的，**前提已经变了**——这条记录本身就是"旧结论要跟着前提走"的例子。

#### `_chat(messages) -> str` — L336 / `stream(messages)` — L352

**职责**：非流式 / 流式调本地模型。`stream` 产出 `(kind, text)`，`kind` 是 `"reasoning"` 或 `"content"`。

**为什么流式要把 thinking 单独分出来**：思考过程不该混进答案正文。前端也把两者分开展示。

#### `prepare(question, top_k=6, expand_hops=1, alpha=0.5, max_blocks=10) -> dict` — L385

**职责**：**先做检索与上下文组装（快）**，把 `messages` 交给生成阶段（慢）。

**为什么拆成 prepare / finalize 两步**：Web 端要先把"查到哪些材料"推给用户（SSE 的 `meta` 事件），让用户在看模型输出的同时就知道依据是什么。检索是秒级，生成是十几秒——分开之后体验完全不同。

#### `finalize(prepared, answer) -> dict` — L411

**职责**：把答案和引用回查结果合成最终返回值。

返回里包含 `answer / citations / secondary_citations / invalid_citations / citation_ok / has_citation / refused`。

#### `verify_citations(answer, contexts) -> dict` — L421 ★

**职责**：**引用三分类回查**。这是这个项目防幻觉的核心机制。

**为什么是三类而不是"对/错"**：

| 类别 | 含义 |
|---|---|
| `cited` | 材料里**确实有这个节点** —— 硬依据 |
| `secondary` | 编号只出现在**材料正文的转述里**（如条文写"按附录B表B.0.2采用"）——模型引它不算幻觉，但也不是直接依据 |
| `invalid` | **材料里根本找不到** —— 判为幻觉 |

**做法**：先从所有材料的文本里抽出"被提到过的编号"集合，再拿答案里的引用去比对。**关键在于第二步用的是"材料正文里提到过"，而不是"材料节点本身"**——否则条文里转述的引用会被全部误判成幻觉。

#### `is_refusal(answer) -> bool` — L453

**职责**：判断模型是不是拒答了。查 `REFUSAL_MARKERS`。

**为什么要判断**：拒答是**期望行为**，不是失败。指标统计时要能把它和"答错了"分开。

#### `answer(question, ...) -> dict` — L457

**职责**：`prepare` + `_chat` + `finalize`，一次性同步问答。notebook 和命令行用这个。

## 七、改代码时该动哪一层

按"你想达到什么效果"来查：

| 你想做的事 | 动哪里 |
|---|---|
| 加一个字段 | `schema.NODE_FIELDS` + `NodeBuilder._base`，然后检查下游三处 |
| 加一种节点类型 | `schema.TYPE_LEVEL` + `NodeBuilder` 加一个 `*_node` 方法 |
| 改编号/引用识别规则 | `schema._REF_PATTERNS`（引用） / `layout` 里对应的正则（版面识别） |
| 某张表读出来是错的 | `layout.real_tables`、`_guess_header_rows`、`flat_header` |
| 某条条文被切碎了 | `parser._assemble`、`parser._consume_items` |
| 条文和它的说明没连上 | `parser._link_explanations`、`_explanation_targets` |
| 某张表查不到值 | `tables.classify_table`、`_pick_key_column`、`build_tool` |
| 检索不到某个术语 | `index.tokenize`（先看它被切成什么）、`DOMAIN_SYNONYMS`（加同义词） |
| 编号查询不准 | `index.mentioned_ids`、`HybridRetriever.search` 里的 `mention_boost` |
| 回答漏掉该带的附表 | `HybridRetriever.search` 里的 `expand_hops` 那一整段 |
| 答案不带条号 / 乱标条号 | `generate.build_system_prompt`、`verify_citations` |
| 查表问题答不对 | `generate._probe_table`、`_direct_lookup`、`_title_overlap` |
| 首字太慢 | `Answerer.__init__` 的 `reasoning_effort`，或 `build_context` 的 `max_blocks` |
| 加一本新规范 | 都不用改——跑 `run_parse.py` 就行 |
